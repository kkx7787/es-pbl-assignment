# Day 4 연습문제 답안 작성 방법

이 문서는 “차트가 나왔습니다”에서 끝내지 않고, 다른 사람이 같은 조건을 재현하고 결과를 확인할 수 있게 답을 쓰는 방법을 설명합니다.

## 1. 답안의 기본 구조

모든 문제는 가능한 한 다음 7개 항목으로 작성합니다.

1. 질문: 무엇을 확인하려 했는가?
2. 시작 상태: Data View, 시간 범위, KQL, filter/control 상태는 무엇인가?
3. 설정: 사용 field, 계산 방식, 차트, 정렬·구간·Top N은 무엇인가?
4. 실제 결과: 실행 후 나온 수치·항목·변화는 무엇인가?
5. 판정: 요구사항을 충족했는가?
6. 근거: 화면 캡처 또는 비교 요청 파일은 어디에 있는가?
7. 해석·다음 행동: 이 결과로 무엇을 판단하며, 무엇은 단정할 수 없는가?

## 2. 좋은 답의 최소 형식

```text
- 질문:
- Data View / index:
- 시간 범위:
- KQL / filter / control:
- field:
- 계산·그룹 방식:
- 차트·정렬·구간:
- 실제 결과:
- 정상/보류/오류 판정:
- 판정 근거:
- 캡처 파일:
- 해석 또는 다음 행동:
- 현재 데이터로 단정할 수 없는 것:
```

모든 문제에서 12개 항목을 반복할 필요는 없습니다. 문제지에 준비된 입력란 중 해당 항목만 채웁니다.

## 3. 나쁜 답과 좋은 답의 차이

### 너무 부족한 답

```text
Bar 차트를 만들었다. 정상이다.
```

누가 다시 만들었을 때 같은 결과가 나오는지 확인할 수 없습니다.

### 재현 가능한 답의 예시

아래 예시는 답의 작성 방식만 보여 주며 실제 문제의 정답이 아닙니다.

```text
- 질문: 유형별 이벤트 수는 어떻게 다른가?
- Data View: my-events
- 시간 범위: 2026-01-01 00:00 ~ 2026-03-31 23:59
- 시작 조건: KQL 없음, filter 없음
- 설정: event_type Top values, Count of records, horizontal Bar, Top 5
- 실제 결과: 5개 유형이 표시됐고 가장 큰 유형은 A였다.
- 판정: 정상
- 근거: evidence/day-04-practice/example-event-type-bar.png
- 해석: A 유형의 처리 비중이 가장 크므로 상세 원인을 추가로 확인한다.
- 한계: 이벤트 수만으로 처리 시간이나 중요도를 판단할 수 없다.
```

좋은 답은 메뉴를 길게 받아쓰는 답이 아니라, 질문·설정·실제 결과·근거·판정이 연결된 답입니다.

## 4. 화면 캡처 작성 규칙

캡처에는 가능한 한 다음 항목이 함께 보여야 합니다.

- Dashboard 또는 Lens 제목
- 적용된 시간 범위
- KQL과 filter pill
- Control의 선택값
- 패널 제목과 실제 값

권장 파일명:

```text
p01-q02-kql-before-after.png
p02-q03-filter-recovery.png
p05-q04-dashboard-before-after.png
p08-q02-cross-check.png
```

비밀번호, API key, 개인 정보, 다른 학생 이름은 캡처하지 않습니다.

## 5. 비교 문제 작성 방법

설정 A와 B를 비교하는 문제는 한 요소만 바꿉니다.

| 비교 항목 | 설정 A | 설정 B | 관찰한 차이 | 최종 선택과 이유 |
|---|---|---|---|---|
| 예: Bar 방향 | vertical | horizontal | 긴 이름이 B에서 더 잘 보임 | B, 레이블 가독성 때문 |

Top N과 정렬 기준을 동시에 바꾸면 무엇 때문에 결과가 달라졌는지 설명하기 어렵습니다.

## 6. 오류 진단 문제 작성 방법

오류가 보이면 바로 차트를 삭제하지 말고 다음 순서로 기록합니다.

1. 증상: 0건, 한 막대만 표시, 전체값 불일치, field 없음 등
2. 마지막 정상 상태
3. 확인 순서: 시간 → Data View → KQL → filter pill → Control → Lens field/집계
4. 발견한 원인
5. 수정한 한 가지
6. 수정 후 실제 값

```text
- 증상:
- 마지막 정상 단계:
- 확인한 항목과 순서:
- 원인:
- 수정:
- 수정 후 결과:
- 재발 방지:
```

`Inspect`는 Dashboard 편집 모드에서 해당 패널의 `Panel menu`에 있습니다. 권한이나 화면 상태로 보이지 않더라도 실패로 판정하지 않고 Discover 또는 제공 요청으로 검증합니다. PDF와 특정 팝업 문구가 보이지 않는 것도 실패가 아닙니다. 현재 환경에서 실제 제공되는 Dashboard filter pill, 화면 캡처, JSON 내보내기를 사용합니다.

## 7. 개인 PBL 문제 작성 방법

쇼핑몰 field 이름을 자신의 주제에 그대로 복사하지 않습니다.

| 먼저 쓸 것 | 작성 질문 |
|---|---|
| 사용자 | 누가 이 Dashboard를 보는가? |
| 판단 | 보고 무엇을 결정하거나 행동하는가? |
| 문서 단위 | 한 문서는 상품·책·여행지·콘텐츠·사건 중 무엇인가? |
| 필요한 field | 범주·수치·상태·날짜 중 무엇이 필요한가? |
| 데이터 적합성 | 실제 mapping과 문서에 존재하는가? |
| 표현 | Metric·Bar·Table·Donut·Line 중 무엇이 질문에 맞는가? |
| 검증 | 어떤 수치나 조건 변화가 나오면 정상인가? |

field가 부족하면 가짜 결과를 만들지 말고 다음 형식으로 씁니다.

```text
- 답할 수 없는 질문:
- 부족한 field:
- mapping type:
- 예시값 3개:
- 값의 범위·범주·비율:
- 한 문서에 값을 만드는 규칙:
- 필요한 문서 수와 이유:
- 생성·수집 방법:
```

개인 데이터가 준비되지 않았으면 공통 `products`로 기능 실습을 완료한 뒤 이 데이터 설계를 제출해도 됩니다.

## 8. 결과 해석 문장 작성 방법

다음 순서를 사용합니다.

`적용 조건 → 핵심값 → 비교 대상 → 판단/다음 행동 → 한계`

문장 틀:

```text
[조건]에서 [핵심값]이 확인됐고 [비교 대상]보다 [차이]가 있었다.
따라서 [다음 행동]을 검토한다. 다만 [없는 field/사건]이 없으므로 [과도한 결론]은 단정하지 않는다.
```

`created_at`이 상품 등록일이라면 판매 추이나 매출 변화라고 쓰지 않습니다.

## 9. 제출 전 자가 점검

- [ ] 실제 실행 결과를 적었다.
- [ ] 질문과 field가 연결된다.
- [ ] 차트와 계산 방식이 연결된다.
- [ ] 시간·KQL·filter/control 상태가 기록됐다.
- [ ] 비교 문제는 한 요소만 바꿨다.
- [ ] 정상/보류/오류 판정에 근거가 있다.
- [ ] 캡처 경로가 존재한다.
- [ ] 현재 데이터로 말할 수 없는 한계를 적었다.
- [ ] 개인 문제는 자신의 field를 사용하거나 데이터 보강 규칙을 작성했다.
