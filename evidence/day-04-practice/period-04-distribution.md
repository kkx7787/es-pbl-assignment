## (공통·필수) 문제 1 — 50,000원 단위 가격 분포

`price`와 Count of records를 사용해 가격대별 Bar를 만드세요. 자동 막대 수를 맞추려고 `Decrease granularity`를 반복하지 말고 `Create custom ranges`를 사용합니다.

권장 구간 예:

- 0 이상 50,000 미만
- 50,000 이상 100,000 미만
- 100,000 이상 150,000 미만
- 150,000 이상 200,000 미만
- 200,000 이상

### 결과 입력

- 실제 입력한 구간: `Create custom ranges`로 5개를 직접 입력했다.
  화면 라벨이 `0 → 50,000`, `50,000 → 100,000`, `100,000 → 150,000`, `150,000 → 200,000`, `200,000 → +∞`로 표시된다.
- 구간 사이 빈틈·중복 확인 방법: 세 가지로 확인했다.
  ① 라벨의 경계 숫자가 앞 구간의 끝과 다음 구간의 시작이 같은 값으로 이어진다(`50,000`이 1구간 끝이자 2구간 시작).
     Lens의 구간은 `lower ≤ value < upper`라 경계값이 한 구간에만 들어간다.
  ② 마지막 구간이 `+∞`로 열려 있어 상한 밖 문서가 빠지지 않는다.
  ③ **다섯 구간 합이 20,000으로 Metric 패널과 일치한다.** 빈틈이 있으면 합이 모자라고 중복이면 넘친다.

| 구간 | 문서 수 | 비율 |
|---|---:|---:|
| 0 ~ 50,000 | 7,304 | 36.52% |
| 50,000 ~ 100,000 | 4,608 | 23.04% |
| 100,000 ~ 150,000 | 2,645 | 13.22% |
| 150,000 ~ 200,000 | 2,550 | 12.75% |
| 200,000 이상 | 2,893 | 14.46% |
| **합계** | **20,000** | 100% |

- 가장 많은 가격 구간: **0 ~ 50,000원**
- 해당 구간 실제 문서 수: **7,304건** (전체의 36.5%)
- 저가 구간이 큰 이유: 카테고리별 가격 범위가 다르기 때문이다.
  `도서`(9,800~48,000), `식품`(5,900~74,000), `뷰티`(7,900~89,000)는 상한이 10만 원 이하라
  전량이 앞 두 구간에 들어간다. 반대로 `전자기기`(19,000~429,000)만 20만 원 이상 구간을 크게 채운다.
  **가격 분포는 상품이 싸다는 뜻이 아니라 어떤 카테고리를 많이 담고 있는지를 보여 준다.**
- 제목: `가격대별 상품 분포`
- 캡처 파일: `p04-q01-price-ranges.png`

## (공통·필수) 문제 2 — 재고 상태 Donut과 기준값 검증

차트 유형 `Pie`에서 `in_stock` Top values와 Count of records를 설정한 뒤, `Style → Appearance → Donut hole → Medium`으로 Donut을 만드세요. 차트 목록에서 Donut을 찾지 않습니다.

### 결과 입력

- true 실제 값: **16,999**
- false 실제 값: **3,001**
- 합계: **20,000**
- 전체 20,000과 일치하는가: **일치한다.** Metric 패널과 같고 `GET /products/_count`(20,000),
  `in_stock: false` KQL 결과(3,001)와도 맞는다. 1교시 Discover에서 확인한 3,001과 동일하다.
- 비율 또는 값 표시 방식: 처음에는 백분율(`true 85%` / `false 15.01%`)로 나왔다.
  비율만으로는 기준값 대조가 어려워 **`Style → Titles and text → Slice values`를 `Integer`로 바꿔**
  실제 건수를 표시했다. 15.01%는 `3,001 ÷ 20,000 = 15.005%`의 반올림 표시라 값 자체는 처음부터 맞았다.
- Donut 만드는 법: 차트 선택기에 `Donut`이라는 유형이 없다. **`Pie`를 만든 뒤
  `Style → Appearance → Donut hole`을 `Medium`으로** 바꿨다.
- 제목: `재고 상태 비율`
- 한 조각만 보일 때 먼저 확인할 조건:
  ① `Number of values`가 1인지(2여야 `true`/`false` 둘 다 나온다)
  ② 상단 KQL·filter pill·Control에 `in_stock` 조건이 걸려 있는지
  ③ 시간 범위가 좁아 한쪽 상태 문서만 남았는지
  ④ 그래도 안 되면 Metric 패널 값을 본다. Metric도 함께 줄었으면 Dashboard 전체 조건이,
     Metric은 20,000 그대로인데 Donut만 이상하면 그 패널의 Lens 설정이 원인이다(2교시 진단과 같은 판별법).
- 캡처 파일: `p04-q02-stock-donut.png`

## (공통·필수) 문제 3 — 월별 상품 등록 Line과 잘못된 해석 수정

`created_at` Date histogram과 Count of records를 사용하고 `Minimum interval`에 `1M`을 입력해 월 단위 Line을 만드세요.

다음 문장을 데이터에 맞게 수정하세요.

> 월별 판매량이 증가하거나 감소하는 모습을 보여 준다.

### 결과 입력

- 선택한 interval: `Date histogram` + **`Minimum interval` `1M`**
- 보이는 월 구간: **2025-08 ~ 2026-08, 13개 버킷** (합계 20,000)

| 구간 | 문서 수 |
|---|---:|
| 2025-08 (부분 달) | **268** |
| 2025-09 ~ 2026-07 (11개월) | 1,566 ~ 1,728, 평균 **1,657** |
| 2026-08 (부분 달) | **1,500** |

- 실제 패널 제목: `월별 상품 등록 분포`
- 수정한 설명 문장:
  > ~~월별 판매량이 증가하거나 감소하는 모습을 보여 준다.~~
  > **월별 상품 등록 건수를 보여 준다. 2025-09부터 2026-07까지 11개월은 1,566~1,728건으로 거의 일정하며
  > 증가·감소 추세가 없다. 양 끝의 2025-08(268건)과 2026-08(1,500건)이 낮은 것은 추세가 아니라
  > 데이터 범위가 2025-08-27에 시작해 2026-08-26에 끝나 두 달이 부분 달이기 때문이다.**
- 첫 점이 낮은 이유 검증: 2025-08은 5일치(08-27~08-31)뿐이다.
  `268 ÷ 5 ≈ 54건/일`이고 온전한 달은 `1,657 ÷ 30 ≈ 55건/일`로 **일평균은 같다.**
  즉 8월에 등록이 적었던 것이 아니라 **기간이 짧았을 뿐**이다.
  마지막 2026-08도 26일치라 1,500건으로 낮게 보인다.
- `created_at`의 실제 의미: **상품이 카탈로그에 등록된 시점.**
  주문·결제·배송 같은 사건이 아니라 데이터가 만들어진 시각이다.
  가운데 11개월이 평평한 것도 생성기가 1년 범위에 균등 난수로 뿌렸기 때문이며,
  실제 사업 활동의 계절성이 아니다.
- 판매 추이를 알려면 추가로 필요한 사건/field:
  **주문 1건 = 문서 1건인 별도 index가 필요하다.** 최소한 `order_date`(date), `product_id`(keyword),
  `quantity`(integer), `amount`(long)가 있어야 한다.
  현재 `products`는 문서 1건이 상품 1개의 현재 상태라 시간축에 쌓이는 사건이 없다.
  `price`는 판매가일 뿐 팔린 기록이 아니고, `updated_at`도 정보 수정 시각이지 거래가 아니다.
- 캡처 파일: `p04-q03-created-line.png`

## (개인·필수) 문제 4 — 분포·비율·시간 중 하나 선택

자기 질문에 필요한 유형 하나만 선택해 설계하거나 만드세요.

| 선택 | 필요한 데이터 | 적합한 질문 예 |
|---|---|---|
| 분포 | 숫자 field | 값이 어느 구간에 몰려 있는가? |
| 비율 | 상태·범주 field | 상태별 구성은 어떠한가? |
| 시간 | 날짜 field | 기간별 문서 수는 어떻게 달라지는가? |

- 선택 유형: **시간** (분포·비율·시간 중 하나)
- 사용자 질문: **"계약이 언제 풀리는가?"**
  스카우팅 리서처가 "지금 미리 봐 둬야 할 자원"을 고르는 데 직접 쓰인다.
- field와 mapping type: **`contract_until` / `date`** (`format` 미지정)
- 그룹/구간/시간 단위: `Date histogram`, **`Minimum interval` `1y`**
  월 단위로 쪼개면 5년 × 12 = 60개 버킷이라 읽히지 않는다. 계약 만료는 연 단위 판단이면 충분하다.
- 차트: **Bar** (Line이 아니다)
  공통 `created_at`은 연속된 흐름이라 Line이 맞지만, 계약 만료는 **연도별로 끊어 비교**하는 값이라
  막대가 낫다. 선으로 이으면 없는 추세가 있는 것처럼 보인다.
- 완료 기준: 5개 막대가 나오고 합이 6,000일 것.

| 연도 | 선수 수 |
|---|---:|
| 2027 | 757 |
| 2028 | **1,584** |
| 2029 | 1,454 |
| 2030 | 1,465 |
| 2031 | 740 |
| 합계 | **6,000** |

- 실제 결과 또는 부족한 데이터: **아직 만들지 않았다.** 7교시에서 만든다.
  위 값은 Dev Tools의 `date_histogram`으로 미리 확인한 기준값이다.
- 해석 시 주의할 한계:
  - **`contract_until`은 계약 만료 시점이지 이적 시점이 아니다.** 2028년이 1,584명으로 가장 많다는 것은
    그해에 **협상 기회가 열리는 선수 수**이지 그해에 이적이 많이 일어난다는 뜻이 아니다.
    공통 실습의 `created_at`을 판매 추이로 읽으면 안 되는 것과 같은 종류의 함정이다.
  - **양 끝 2027·2031이 낮은 것도 추세가 아니다.** 생성 범위가 `2027-06-30 ~ 2031-06-30`이라
    두 해가 반년치씩만 들어 있다. 4교시 공통 문제 3의 부분 달 문제와 같은 구조다.
    실제로 757과 740은 가운데 세 해(1,454~1,584)의 약 절반이다.

## (선택 도전) 문제 5 — 가격 구간 대안 비교

50,000원 구간과 자신이 설계한 다른 구간을 비교하세요. field와 Count는 유지합니다.

| 비교 | 50,000원 단위 | 대안 구간 |
|---|---|---|
| 막대 수 | 5개 | (미실행) |
| 읽기 쉬움 | (미실행) | (미실행) |
| 판단에 유용함 | (미실행) | (미실행) |

- 최종 선택과 이유: **미실행.** 선택 도전이라 필수 4문제를 먼저 마쳤다.
  설계만 적어 두면, 대안으로는 **로그 성격의 비균등 구간**(0~2만 / 2~5만 / 5~10만 / 10~20만 / 20만 이상)을
  시험해 볼 만하다. 현재 균등 5만 원 구간은 첫 칸에 36.5%가 몰려 그 안의 분포가 안 보인다.
  다만 비균등 구간은 막대 폭과 실제 범위가 어긋나 오해를 부를 수 있어, 바꾼다면 라벨을 명확히 달아야 한다.
