## (개인·필수) 문제 1 — 사용자와 판단 하나로 좁히기

Dashboard를 사용할 사람 한 명과 그 사람이 내릴 판단 하나를 정하세요.

### 답안

- 내 주제: 26/27 시즌 프리미어리그 스카우팅 선수 검색
- 한 문서의 의미: **선수 1명의 현재 상태 스냅샷.** 사건이 아니라 대상이다. 총 6,000건.
- 사용자 한 명: **하위 리그·유스 자원 영입을 검토하는 스카우팅 리서처 1명.**
  구단 전체나 감독이 아니라, 후보 목록을 만들어 보고하는 실무자 한 사람이다.
- 사용자가 반복해서 하는 일: 매주 관찰 대상 명단을 갱신한다.
  6,000명 전부를 볼 수는 없으므로 **어디를 먼저 볼지 매번 다시 정해야 한다.**
- Dashboard를 보고 결정할 것: **다음 이적시장에 누구를 먼저 보러 갈지.**
  구체적으로 ① 어느 리그를 우선 훑을지 ② 어느 구단에 접촉할지 ③ 언제 계약이 풀리는 자원을 지금 봐 둘지.
- 결정 뒤 수행할 행동: 우선순위 리그·구단을 정해 **현장 관찰 일정을 잡고 후보 명단을 좁힌다.**
- 사용자에게 필요 없는 정보:
  - `height_cm`, `nationality` — 이 판단 단계에서 쓰이지 않는다. 후보를 좁힌 뒤 개별 검토에서 본다.
  - `first_name`/`last_name` — `name`이 이미 합친 값이라 중복이다.
  - `is_synthetic` — 데이터 출처 표시용 운영 field다.
  - `appearances`/`goals`/`assists` — **독립 난수라 서로 모순된다**(4경기 출전에 26골 등). 판단에 쓰면 안 된다.

`모든 사용자`, `전체 현황`, `데이터를 본다`처럼 넓은 표현은 한 사람과 한 행동으로 좁힙니다.

## (개인·필수) 문제 2 — 서로 중복되지 않는 질문 4개

다음 역할을 하나씩 사용해 질문 4개를 작성하세요.

1. 전체 규모
2. 그룹 비교
3. 수치 분포 또는 정확한 값 비교
4. 상태 비율 또는 시간 변화

| 번호 | 분석 질문 | 질문의 답으로 내릴 판단 | 다른 질문과 겹치지 않는 이유 |
|---|---|---|---|
| **Q1 전체 규모** | 검토 대상 선수 풀은 몇 명인가? | 이번 주 작업량의 기준을 잡는다. 조건을 걸었을 때 몇 명까지 좁혀졌는지 판단하는 분모가 된다 | 유일하게 **집합의 크기**를 답한다. 나머지 셋은 집합 안의 구성을 답한다 |
| **Q2 그룹 비교** | 어느 리그에 후보가 몰려 있는가? | 우선 훑을 리그를 정한다 | `league` 한 축의 **건수 비교**다. Q3는 두 지표를 함께 보고, Q4는 시간축이다 |
| **Q3 정확한 값 비교** | 어느 구단에 몇 명이 있고 그 구단의 몸값 수준은 어떤가? | 접촉할 구단을 정하고 예산 감당 여부를 가늠한다 | 유일하게 **건수와 금액 두 지표를 한 행에서** 비교한다. Q2는 건수만 본다 |
| **Q4 시간 변화** | 계약이 언제 풀리는가? | 지금 미리 봐 둘 자원의 연도를 정한다 | 유일하게 **날짜축**이다. 나머지는 시점 개념이 없다 |

- 보조 질문(Q5, 상태 비율): 주발 구성은 어떤가? 왼발 자원이 얼마나 희소한지 확인해
  Q1~Q4로 좁힌 후보 안에서 희소 자원을 놓치지 않게 한다.
  역할이 "상태 비율"이라 Q2(그룹 비교)와 겹칠 소지가 있어 **필수 4개에는 넣지 않고 보조로 둔다.**

## (개인·필수) 문제 3 — 질문별 field 존재 여부 점검

각 질문에 필요한 field가 실제 mapping과 문서에 있는지 확인하세요.

| 질문 | 필요한 field | mapping type | 실제 존재 | 값이 충분히 분포 | 가능/가공 필요/추가 필요 |
|---|---|---|---|---|---|
| Q1 | (문서 수) | — | O | 6,000건 | **가능** |
| Q2 | `league` | `keyword` | O | 8종, 498~932로 분포 | **가능** |
| Q3 | `club`, `market_value_eur` | `keyword`, `long` | O | 구단 10종 각 583~638 / 금액 223,829~89,975,240 | **가능** |
| Q4 | `contract_until` | `date` (format 미지정) | O | 2027~2031, 740~1,584 | **가능** |
| Q5(보조) | `preferred_foot` | `keyword` | O | 3종, 224~4,304 | **가능** |

- 존재 확인 방법: Data View `PL 스카우팅 선수`의 **Available fields 23개**에서 확인했고,
  1교시 Discover에서 `player_id`·`name`·`club`·`league`·`age`·`preferred_foot`·`contract_until` 7개를
  실제 열로 띄워 값이 채워져 있는 것을 봤다.
- 분포 확인 방법: Dev Tools `terms`·`stats`·`date_histogram` 집계로 각 field의 실제 분포를 미리 뽑았다.
  **고유값이 1개거나 한쪽에 쏠려 차트가 무의미해지는 field는 없다.**
- 현재 데이터로 바로 만들 수 있는 질문 수: **4개 전부 + 보조 1개.**
- 선택한 A/B/C 경로: **A — 개인 데이터로 제작**
- 선택 이유: 범주형(`league`, `club`, `preferred_foot`), 수치형(`market_value_eur`),
  날짜형(`contract_until`)이 모두 있어 Metric·Bar·Table·Donut을 전부 실제 field로 만들 수 있다.
  공통 `products`로 대체하거나 데이터를 새로 만들 이유가 없다.
  다만 **답할 수 없는 질문이 따로 있으며**(문제 4) 그 부분만 보강 설계로 남긴다.

### 공통 데이터와 다른 점 — 미리 알아 둘 것

| 항목 | 공통 `products` | 개인 `scout-players-2627` |
|---|---|---|
| 범주 분포 | `category` 8종 각 2,500 (완전 균등) | `league` 8종 **498~932로 기울어짐** |
| Top N | `brand` 40종 → `Other` 생기고 accuracy 경고 | `club` **10종** → `Other` 없고 경고 없음 |
| 시간축 | `created_at` 1년, 양 끝이 부분 달 | `contract_until` 5년, **양 끝이 반년치** |

`league` Bar가 평평하지 않은 것은 오류가 아니라 `weighted_choice` 규칙의 결과다.

## (개인·필수) 문제 4 — 부족한 데이터 생성 규칙 설계

현재 답할 수 없는 질문 하나를 선택하고 필요한 데이터를 구체화하세요.

- 답할 수 없는 질문: **"이적 시장이 실제로 어떻게 움직였는가?"**
  세부적으로는 "이적이 얼마나 성사됐나", "이적료 수준이 시간에 따라 어떻게 변했나",
  "어느 구단이 하위 리그에서 자주 영입하나"다.
  현재 문서 1건이 **선수 1명의 현재 상태 스냅샷**이라 시간축에 쌓이는 사건이 없다.
  `contract_until`로 Line을 그릴 수는 있지만 그건 사건의 흐름이 아니라 만료일 분포다.
- 부족한 field: `transfer_date`, `fee_eur`, `from_club`, `to_club`, `player_id`(연결키), `season`, `window`
- mapping type:

| field | type | 비고 |
|---|---|---|
| `transfer_id` | `keyword` | 업무 ID, `_id`와 같은 값 |
| `player_id` | `keyword` | `scout-players-2627`의 `player_id`와 연결 |
| `transfer_date` | `date` | format 미지정 (ISO 8601) |
| `fee_eur` | `long` | 0 포함 |
| `from_club` / `to_club` | `keyword` | 기존 `clubs` 후보 10개 |
| `season` | `keyword` | 3종 |
| `window` | `keyword` | 2종 |

- 예시값 3개:
  1. `{ "transfer_id": "T-00001", "player_id": "P-0024", "transfer_date": "2026-01-18T00:00:00Z", "fee_eur": 12500000, "from_club": "Riverton Athletic", "to_club": "Northgate City", "season": "2025/26", "window": "winter" }`
  2. `{ "transfer_id": "T-00002", "player_id": "P-0067", "transfer_date": "2025-08-03T00:00:00Z", "fee_eur": 0, "from_club": "Ashford United", "to_club": "Harrowgate FC", "season": "2025/26", "window": "summer" }`
  3. `{ "transfer_id": "T-00003", "player_id": "P-0233", "transfer_date": "2027-07-11T00:00:00Z", "fee_eur": 48200000, "from_club": "Kingsmere FC", "to_club": "Elderfield Town", "season": "2026/27", "window": "summer" }`
- 범주라면 고유값 수: `from_club`/`to_club` 각 **10개**(기존 구단 목록 재사용),
  `season` **3개**(`2024/25`, `2025/26`, `2026/27`), `window` **2개**(`summer`, `winter`)
- 수치라면 최소·최대·대표 구간: `fee_eur` **0 ~ 150,000,000**.
  대표 구간은 0(자유계약) / 1~1,000만 / 1,000만~5,000만 / 5,000만 이상 네 구간으로 나눠 Bar를 만든다.
  현재 `market_value_eur`(200,000~90,000,000)보다 상한을 높게 잡는다. 실제 이적료는 시장가치를 웃도는 경우가 많다.
- 상태라면 예상 비율: **자유계약(`fee_eur = 0`) 20%.**
  나머지 80%는 유료 이적이다. 이 비율이 있어야 Donut으로 "돈 안 드는 영입 비중"을 볼 수 있다.
- 날짜라면 기간과 단위: **2024-07-01 ~ 2027-06-30 (3시즌), 월 단위 집계.**
  이적 시장은 여름·겨울에 몰리므로 월 단위여야 그 봉우리가 보인다. 연 단위면 사라진다.
- 다른 field와 필요한 관계: **세 가지 종속이 반드시 필요하다.**
  1. `from_club ≠ to_club` — 같으면 이적이 아니다
  2. `transfer_date`의 월이 `window`와 맞아야 한다 (`summer` = 6~8월, `winter` = 1~2월)
  3. `player_id`가 `scout-players-2627`에 실재해야 한다
  **현재 생성기는 field 간 종속을 표현하지 못한다.** `detailed_position`과 `trait`가 독립 난수라
  "골키퍼인데 강점이 측면 돌파"인 문서가 생긴 것과 같은 한계다.
  따라서 생성 후 후처리하거나 `FixedDocumentsFile`로 경계 사례를 고정해야 한다.
- 한 문서를 생성하는 규칙:
  1. `player_id`를 기존 6,000명에서 뽑는다 (한 선수가 여러 번 이적할 수 있으므로 중복 허용)
  2. `from_club`은 그 선수의 현재 `club`으로 고정, `to_club`은 **나머지 9개 중에서** 뽑는다
  3. `window`를 `summer` 70% / `winter` 30%로 뽑고, 해당 월 범위 안에서 `transfer_date`를 뽑는다
  4. 20% 확률로 `fee_eur = 0`, 나머지는 그 선수 `market_value_eur`의 **0.7~1.5배** 범위에서 뽑는다
  5. `season`은 `transfer_date`로부터 계산한다 (7월 이후면 다음 시즌)
  4번이 핵심이다. 이적료를 시장가치와 무관한 난수로 뽑으면 "몸값 200만 유로 선수의 이적료 1억 유로"가 나와
  현재 데이터와 같은 정합성 문제를 반복하게 된다.
- 필요한 문서 수와 이유: **3,000건 이상.**
  36개월 × 리그 8개로 나눠도 버킷당 약 10건이 남아 월별 Line이 끊기지 않는다.
  1,000건이면 버킷당 3건이라 겨울 이적 시장 같은 작은 봉우리가 노이즈에 묻힌다.
- seed 고정 여부: **고정한다.** 현재 개인 데이터와 같은 방식으로 `$Seed`를 설정 파일에 박아
  누구나 같은 파일을 재생성할 수 있게 한다. `generation-summary.json`의 `bulk_sha256`으로 검증한다.
- 생성 후 검증 방법:
  1. `_count`가 생성 건수와 일치하는가
  2. `from_club == to_club`인 문서가 **0건**인가 (`script` query 또는 로컬 검증)
  3. `window`별 `transfer_date` 월 분포가 규칙과 맞는가 (`summer`가 6~8월에만 있는가)
  4. `fee_eur = 0`의 비율이 20% 근처인가
  5. `player_id`가 `scout-players-2627`에 없는 값이 있는가
  6. 월별 `date_histogram`에 빈 버킷이 없는가

“랜덤으로 많이 만든다”는 규칙이 아닙니다. Dashboard에서 비교·분포·필터 결과가 나타나도록 값의 범위와 관계를 적습니다.
